# Harness Engineering Skill

## 概念定義

```
AIエージェント = モデル + ハーネス
```

**ハーネス**とは、モデルを包み込み、外部環境と接続し、その行動を制限・拡張・監視する仕組みの総体。
モデルの単体性能よりも、ハーネスの設計品質が成果物の差を決定づける。

### ハーネスが担う5つの役割

| 役割 | 内容 |
|---|---|
| 入力制御 | モデルに何を見せ、何を使わせるかを最適化（不要情報の排除） |
| ガードレール | 特定コマンドの拒否・確認要求など、安全性の担保 |
| 外部監視 | モデルの挙動を外部から継続的にモニタリング |
| フィードバックループ | 失敗時の修正・再実行プロセスの管理 |
| 外部調節 | ユーザー/システム視点でのパラメーター・動作の調整 |

### 進化の系譜

```
プロンプトエンジニアリング
  → コンテキストエンジニアリング（何を注入するか）
    → ハーネスエンジニアリング（環境全体を設計する）
```

## Phase 1: 現状読み込み（並列実行）

以下をすべて **並列で** 読み込む。完了前にPhase 2へ進まない。

1. `CLAUDE.md`（プロジェクトルート）
2. `.claude/settings.json`（プロジェクトレベル）
3. `~/.claude/settings.json`（グローバル）
4. `~/.claude/CLAUDE.md`（グローバル指示）
5. `~/.claude/projects/<project-slug>/memory/MEMORY.md`（存在する場合）
6. スタック判定: `vercel.json`, `package.json`, `pyproject.toml` など

同時に並列実行:
- `git log --oneline -10` — 直近の変更履歴
- `ls`（プロジェクトルート）— ディレクトリ構成

## Phase 2: 6次元スコアリング（各0〜5点）

### 1. コンテキスト（CLAUDE.md 品質）

- プロジェクトスコープ・グローバルスコープに存在するか
- 技術スタック・主要コマンド・ディレクトリ構成が正確に記述されているか
- **機械的に速く読める形式**か（ヘッダー・リスト・正確なコマンド）
- 抽象的すぎず、具体的すぎず（適切な粒度）

**減点対象**: `## Commands` セクションの欠如、陳腐化したアーキテクチャ図、ナラティブな散文、不要な情報の詰め込み

### 2. ツール（権限設定）

- 読み取り専用ツール（Glob, Grep, Read）が事前承認されているか
- 繰り返し許可を求めるパターンがないか（摩擦の検出）
- `allowedTools` が適切にスコープされているか

**減点対象**: `settings.json` の不在、必要な読み取りツールの未承認、過剰なワイルドカード

### 3. ガードレール（フック）

4種のフックパターンが揃っているか確認:

| パターン | タイミング | 目的 |
|---|---|---|
| Safety Gates | PreToolUse | 破壊的操作をブロック |
| Quality Loops | PostToolUse | ファイル書き込み後にリンター実行・自己修正 |
| Completion Gates | Stop | 完了宣言前にテスト通過を確認 |
| Observability | PostToolUse | エージェントの意図と結果を外部パイプラインへ記録 |

リンター選定基準（速度優先）:
- Python: **Ruff**
- TypeScript/JS: **Oxlint**（リント）+ **Biome**（フォーマット）

**減点対象**: フック未設定、フォーマット/リントをモデルの判断に委ねている

### 4. モニタリング（メモリ）

- `~/.claude/projects/<slug>/memory/MEMORY.md` が存在するか
- メモリエントリが直近のgit履歴と矛盾していないか（陳腐化の検出）
- ユーザーのフィードバックパターンと設計決定が記録されているか

**減点対象**: メモリシステムの不在、現在のコードと矛盾するエントリ、フィードバックメモリの欠如

### 5. フィードバックループ（自己修正）

- テスト/リント/型チェックコマンドが CLAUDE.md に記載されているか
- モデルがユーザーに確認せずに自分の変更を検証できるか
- 繰り返し発生する失敗パターンがメモリに記録されているか

**減点対象**: テストコマンドの未記載、リンターの不在、自己チェック手段のなさ

### 6. レイヤーアーキテクチャ（5層確認）

- `CLAUDE.md` がグローバルとプロジェクトの両スコープで定義されているか
- `.claude/rules/` に `globs` フロントマター付きのドメイン別ルールが存在するか
- 再利用可能なワークフローがスキル（`.claude/skills/`）として定義されているか
- 専門エージェントが `.claude/agents/` に定義されているか
- `settings.json` で権限とSafety Gatesがスコープされているか

**減点対象**: `rules/` ディレクトリの不在、CLAUDE.md のモノリシック化（委譲なし）、エージェント未定義

## Phase 4: 承認された変更の実装

| 変更種別 | 実装方法 |
|---|---|
| CLAUDE.md 更新 | Edit または Write |
| settings.json 権限 | `.claude/settings.json` を直接 Edit |
| フック追加 | `settings.json` の `hooks` 配列を Edit |
| 新規メモリファイル | `~/.claude/projects/<slug>/memory/<topic>.md` に Write |
| MEMORY.md インデックス更新 | `~/.claude/projects/<slug>/memory/MEMORY.md` を Edit |
| Rules ファイル追加 | `.claude/rules/<topic>.md` に Write（`globs` フロントマター必須） |
| エージェント追加 | `.claude/agents/<role>.md` に Write |

各ファイル変更後、何をなぜ変更したかを1文で確認する。

## 設計の原理原則

### コンテキストは有限のRAM

- **段階的開示**: スキルやドキュメントを一度にすべて渡さず、モデルが必要に応じて参照しに行く仕組みにする
- **ツールの最小化**: ツールを詰め込みすぎるとコンテキストを圧迫する。必要最小限に留める
- **決定論的制御の優先**: AIにしかできないことはAIに任せ、決定論的に解ける処理（リント・フォーマット・型チェック）はフックで自動化する

### ジェネレーター・エバリューエーター・プランナー（3エージェントパターン）

単一エージェントで生成と評価を兼ねさせない（LLMは自分の出力を過剰評価する傾向がある）:

| 役割 | 責務 |
|---|---|
| プランナー | 課題を俯瞰し、タスクを分解・計画立案する |
| ジェネレーター | 計画に基づき、具体的な成果物を作成する |
| エバリューエーター | 懐疑的な視点で成果物を検証し、フィードバックを行う |

### アンチパターン（避けること）

| アンチパターン | 症状 | 対処 |
|---|---|---|
| 過剰な制御 | 制約が厳しすぎてモデルの創造性が死ぬ | 必要最小限のルールに絞り、モデルが賢くなることを前提にする |
| ドキュメント肥大化 | CLAUDE.md が巨大化し注意力が分散する | ドメイン別に `rules/` へ委譲、段階的開示を使う |
| 不適切な粒度 | 具体的すぎて自由度がない or 抽象的すぎて迷う | 適切なバランスを意識し、定期的に粒度を見直す |
| Gen/Eval 混在 | 生成と検証を同一エージェントに担わせる | 評価者エージェントを分離し、客観的な検証を確保する |

## 導入ステップ（優先順位付き）

1. **設定ファイルの整備** — CLAUDE.md と settings.json を整理し、基本動作を定義する
2. **フックによる自動化** — コードフォーマッター・リントなどの決定論的処理を自動化する
3. **検証手段の提供** — CLIツールやテスト実行コマンドをエージェントが自律的に使える環境を整える
4. **評価ループの構築** — ジェネレーターとエバリューエーターを分離し、フィードバックによる品質向上サイクルを導入する
5. **継続的改善** — 実行結果に基づき、スキル・制御パラメーター・メモリを逐次アップデートする
