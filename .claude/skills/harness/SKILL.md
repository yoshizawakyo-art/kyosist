# Harness Engineering Skill — 100-Point Continuous Improvement

このスキルは Claude Code の**ハーネス品質を 8 次元スコアリングで定量評価し、95 点超過まで段階的に改善する** メタスキルです。

**使う場面**:
- 新規プロジェクト立ち上げ時にハーネスゼロから構築
- CLAUDE.md や settings.json が陳腐化したプロジェクトを監査
- コンテキスト肥大化（Context Rot）で精度が低下している場合
- Safety Gates や ツール権限が弱く、自動化が進んでいない場合
- Gen/Eval 分離やモニタリングのような高度な仕組みを導入したい場合

**出力**: スコアリング報告書 + 優先度付き改善ロードマップ + 次ステップの明確化

---

## 概念定義

```
AIエージェント = モデル + ハーネス
```

**ハーネス**とは、モデルを包み込み、外部環境と接続し、その行動を制限・拡張・監視する仕組みの総体。
モデルの単体性能よりも、ハーネスの設計品質が成果物の差を決定づける。

### ハーネスが担う5つの役割

| 役割 | 内容 |
|---|---|
| 入力制御 | モデルに何を見せ、何を使わせるかを最適化（不要情報の排除、Context Rot 防止） |
| ガードレール | 破壊的操作ブロック、安全性担保、リスク優先順位の明確化 |
| 外部監視 | エージェント挙動の継続監視、生成コード品質の検証 |
| フィードバックループ | 失敗パターンの記録、自己修正、継続改善サイクル |
| 外部調節 | パラメーター・権限・プロセスの段階的最適化 |

### ハーネス進化の系譜

```
プロンプトエンジニアリング（何を言うか）
  ↓
コンテキストエンジニアリング（何を見せるか）
  ↓
ハーネスエンジニアリング（環境全体を設計する）
  ↓
採点型ハーネスエンジニアリング（継続改善で95点超を目指す）
```

## Phase 2: 8次元スコアリング（100点ベース）

各観点 0-10 点 × 8 = **最大 100 点**。95 点超過までの継続改善を運用とする。

### 1. コンテキスト品質（10点）

**評価基準**:
- ✅ グローバル・プロジェクト両スコープに CLAUDE.md 存在（3点）
- ✅ 技術スタック・コマンド・ディレクトリ構成が正確・最新（3点）
- ✅ 機械的に速く読める（ヘッダー・リスト・コード例）（2点）
- ✅ 抽象度が適切：具体的すぎず、抽象的すぎず（2点）

**減点**: Commands 欠如（-2）、陳腐化（-3）、散文的（-2）、過剰情報（-2）

### 2. 入力制御・段階的開示（10点）

**評価基準**:
- ✅ スキル（`.claude/skills/`）が機能別に分割されている（3点）
- ✅ Rules（`.claude/rules/`）がドメイン別に存在、globs フロントマター付き（3点）
- ✅ Context Rot 対策：不要情報の排除・メモリ外部化（2点）
- ✅ Just-in-Time ロード仕組みが機能している（2点）

**減点**: スキル不足（-2）、Rules 未整理（-2）、モノリシック CLAUDE.md（-3）

### 3. ガードレール・Safety Gates（10点）

**評価基準**:
- ✅ PreToolUse フック：破壊的操作検出・確認（3点）
- ✅ Quality Loops：リント・フォーマット自動実行・自己修正（3点）
- ✅ Completion Gates：完了前にテスト通過を強制（2点）
- ✅ リスク優先順位の明確化：高/中/低リスク分類（2点）

**減点**: フック未設定（-3）、手動判断に頼る（-2）、リスク分類なし（-2）

### 4. ツール権限・摩擦最小化（10点）

**評価基準**:
- ✅ 読み取りツール（Glob/Grep/Read）事前承認（2点）
- ✅ 繰り返し許可を求めるパターンがない（検出：-3）（2点）
- ✅ allowedTools が適切にスコープ（2点）
- ✅ settings.json で権限が明確に定義（2点）
- ✅ ツール使用摩擦が低い（ユーザー認識ベース）（2点）

**減点**: settings.json 不在（-4）、権限不足（-3）、過剰ワイルドカード（-2）

### 5. Gen/Eval 分離・コードレビュー体制（10点）

**評価基準**:
- ✅ Codex（ジェネレーター）と Claude（エバリューエーター）の責務分離（3点）
- ✅ pdca-check-reviewer など評価エージェントが定義されている（2点）
- ✅ リスクベースレビュー（優先順位付け、自動化、機密検知）（3点）
- ✅ AI生成コード特有問題の対処ガイド（既存機能再実装等）（2点）

**減点**: 責務混在（-4）、評価エージェント不在（-3）、リスク分類なし（-2）

### 6. モニタリング・フィードバック（10点）

**評価基準**:
- ✅ メモリシステム存在・最新化（MEMORY.md + 個別ファイル）（3点）
- ✅ メモリが git 履歴と矛盾していない（陳腐化検出）（2点）
- ✅ フィードバック記録：ユーザーの指示・失敗パターン（3点）
- ✅ 失敗パターンをルール・スキルに反映（2点）

**減点**: メモリ不在（-4）、矛盾エントリ（-2）、フィードバック記録なし（-3）

### 7. 自動化・決定論的制御（10点）

**評価基準**:
- ✅ テスト/リント/型チェックコマンド CLAUDE.md に記載（2点）
- ✅ エージェント自律検証：ユーザー確認なしで自己チェック可（2点）
- ✅ リンター自動実行（Python: Ruff、JS: Oxlint+Biome）（2点）
- ✅ CI/CD フック統合（デプロイ前の自動検証）（2点）
- ✅ 冪等性・自己修正能力が組み込まれている（2点）

**減点**: コマンド記載なし（-2）、手動判断に頼る（-2）、自動化なし（-4）

### 8. レイヤーアーキテクチャ・採点継続改善（10点）

**評価基準**:
- ✅ 5層アーキテクチャ整備：CLAUDE.md / Rules / Skills / Agents / Settings（2点）
- ✅ 採点式ワークフロー導入：95点超過目標の運用が定義されている（2点）
- ✅ スコアリング履歴記録：改善トラック可視化（2点）
- ✅ 継続改善サイクル：スコア低い項目を優先タスク化（2点）
- ✅ 産業標準・ベストプラクティス反映（IPC基準並み）（2点）

**減点**: 層構造が不明確（-2）、採点記録なし（-2）、改善計画なし（-3）

## スコア計算式

```
総点数 = Σ(各観点の点数) / 80 × 100
目標値: ≥ 95 点

例:
- 現状: 72/80 = 90点 → 改善余地あり
- 目標達成: 76/80 = 95点 → ターゲット達成
```

### スコア計算ウォークスルー例

**プロジェクト: 新規 Next.js + FastAPI プロジェクト**

| 観点 | 配点 | 評価の根拠 | スコア |
|---|---|---|---|
| 1. コンテキスト品質 | 10 | CLAUDE.md が存在・最新 +3、技術スタック記載 +3、形式が見やすい +2、抽象度OK +2 | 10/10 |
| 2. 入力制御 | 10 | スキル3個 +2、Rules 3個 +2、Context Rot 対策が部分的 +1、Just-in-Time ロードが不完全 +1 | 6/10 |
| 3. ガードレール | 10 | PreToolUse フック未設定 -3、Quality Loops 部分的 +1、Completion Gates なし -2、リスク分類なし -2 | 3/10 |
| 4. ツール権限 | 10 | settings.json 存在 +2、権限明確 +2、摩擦が大きい -1 | 7/10 |
| 5. Gen/Eval 分離 | 10 | 責務分離ぼんやり +1、評価エージェント未設定 -3、リスク分類なし -2 | 3/10 |
| 6. モニタリング | 10 | メモリシステムなし -4、フィードバック記録なし -3 | 2/10 |
| 7. 自動化 | 10 | テスト / リント記載あり +2、リンター一部実装 +1、自動化不足 -1 | 6/10 |
| 8. レイヤー | 10 | 層構造が初期段階 +1、採点式未導入 -2、改善計画未定義 -2 | 2/10 |
| **合計** | **80** | | **39/80** |
| **総合点** | **100** | 39/80 × 100 = **48.75 点** | **49点** |

**診断**: スコア 49 点は初期段階。高インパクト改善（観点3・5・6）から着手すべき。

### スコア計算ツール

**方法1: スプレッドシート（推奨）**

Google Sheets / Excel で以下テンプレートを作成：
- A 列: 観点名（1-8）
- B 列: 配点（固定 10）
- C 列: 採点者評価（0-10 の記述）
- D 列: スコア（=C）
- E 列: 理由・メモ
- F 列: 改善案

最終行で `=SUM(D2:D9)/80*100` で総合点自動計算

**方法2: JSON 形式（プログラム連携）**

```json
{
  "project": "my-project",
  "audit_date": "2026-05-07",
  "scores": {
    "context_quality": 8,
    "input_control": 6,
    "guardrails": 4,
    "tool_authority": 7,
    "gen_eval_separation": 3,
    "monitoring": 2,
    "automation": 6,
    "layer_architecture": 2
  },
  "total_score": "Σ(scores) / 80 * 100"
}
```

**方法3: マークダウンテーブル（この SKILL.md 形式）**

上記「スコア計算ウォークスルー例」のテーブル形式で IMPROVEMENT_REPORT.md に記載

## 設計の原理原則

### 1. AIエージェント進化パラダイム

**エージェント = モデル + ハーネス**

- **探索 (Explore)** — 現状把握、プランモード
- **計画 (Plan)** — タスク分解、実装方針策定、人間承認
- **実装 (Implement/Do)** — エージェント（Codex等）が自律実行
- **コミット (Commit)** — PR作成・マージ、人間による最終判定

自己検証能力が成功の鍵：テスト・スクリーンショット・期待値をエージェント自身に提供し、自己チェックさせる。

### 2. コンテキスト・エンジニアリング（有限のRAM管理）

```
情報過多 (Context Rot) → 注意力低下 → 精度低下
```

対策:
- **段階的開示** — スキル・ルール・メモリを Just-in-Time でロード
- **不要情報の排除** — 古い設計図、無関係なナラティブを削除
- **外部化** — 重要な判断・失敗パターンをメモリファイルに外部化
- **圧縮** — セッション長が増えたら `/compact` で不要情報を削除

### 3. Gen/Eval 分離（3エージェントパターン）

LLMは自分の出力を過剰評価する傾向があるため、生成と検証を分離：

| 役割 | 責務 | 実装例 |
|---|---|---|
| **プランナー** | 要件整理、タスク分解、実装順序 | Claude 主導 |
| **ジェネレーター** | 計画実行、コード生成 | Codex / 専門エージェント |
| **エバリューエーター** | 超厳格コードレビュー、最終判定 | pdca-check-reviewer / senior-code-reviewer |

原則：ジェネレーターの成果物を、ジェネレーター自身で最終承認しない。

### 4. リスクベースのコードレビュー・優先順位付け

すべての変更に同じ深さのレビューを適用しない：

| リスク | 対象例 | レビュー深さ | 自動化 |
|---|---|---|---|
| **高** | 認証、暗号化、課金、DB変更 | ⭐⭐⭐⭐⭐ 最厳格 | なし（人間必須） |
| **中** | API仕様、UI変更、複数ファイル | ⭐⭐⭐ 厳格 | 基本チェック自動化 |
| **低** | ドキュメント、テスト追加 | ⭐ 通常 | リント・フォーマット自動化 |

機密情報（API キー）の検知は必ず自動スキャン。

### 5. AI生成コード特有の課題と対策

**問題例**:
- 既存ユーティリティの再実装
- 存在しないモジュールのインポート
- 組織標準（命名・責務・層構造）からの逸脱

**対策**:
- 開発者は「AIコードの最初の査読者」として、システム整合性を確認
- `common/`（汎用）と `features/`（機能固有）の境界を厳格に保つ
- エバリューエーターが既存実装との重複をチェック

### 6. 決定論的制御の優先化

AIにしかできないことはAIに任せ、決定論的に解ける処理は自動化：

- **AI判断** — アーキテクチャ設計、エラーハンドリング戦略
- **自動化**（フック） — リント、フォーマット、型チェック、テスト実行

リント・フォーマット・型チェックを「人間の判断」に委ねてはいけない。

### 7. アンチパターン（避けること）

| アンチパターン | 症状 | 対処 |
|---|---|---|
| 過剰な制御 | 制約が厳しすぎてモデルの創造性が死ぬ | ルール最小化、段階的な制約導入 |
| ドキュメント肥大化 | CLAUDE.md が巨大化し注意力が分散 | Rules・Skills へ委譲、段階的開示 |
| 不適切な粒度 | 具体的すぎる / 抽象的すぎる | 定期的な粒度見直し、スコアで検証 |
| Gen/Eval 混在 | 自己評価バイアスで品質低下 | 評価エージェントを分離 |
| Context Rot 放置 | 古い情報が精度を低下させる | 月 1 回の陳腐化チェック、メモリ更新 |

## トラブルシューティング

### Q: Phase 1 で必要なファイルが見つからない

**症状**: `.claude/settings.json` が存在しない、または CLAUDE.md がない

**対処**:
1. ファイルが本当に不在なのかを確認
   ```bash
   test -f .claude/settings.json && echo "exists" || echo "missing"
   test -f ~/.claude/CLAUDE.md && echo "exists" || echo "missing"
   ```
2. **ファイルなしの場合、それ自体がスコア減点要因**（観点4・7・8で大きく減点）
3. 改善計画に「settings.json の初期化」を追加

### Q: スコアが 50 点以下で改善が進まない

**症状**: スコアリング後、何を改善すればよいか不明。複数観点が同時に低い

**対処**:
1. **Phase 3 の改善ロードマップをユーザーと共有**し、「どの改善から始めるべきか」を相談
2. 通常は以下の順で改善する（ROI 高い順）:
   - **観点4（ツール権限）** — settings.json 整備（すぐに効果）
   - **観点1（コンテキスト品質）** — CLAUDE.md の明確化（段階的効果）
   - **観点7（自動化）** — リント・テストコマンド追加（中期効果）
   - **観点3・5・6** — より複雑な仕組み（後期改善）
3. 改善ロードマップが不明確な場合は、手動で案を策定してから進める

### Q: Phase 2 で 8 観点のスコアリング結果が「きれいな数字」になってしまう

**症状**: 各観点が「0, 5, 10」のような端数のない数字になり、不自然に見える

**対処**:
1. **スコアリングは定量的ではなく定性的評価**なので、「5.5」「7.3」などの端数は自然
2. 採点基準の「複数の小項目を部分点で評価」することで、より精密なスコアが出る
3. 粗いスコア（0/5/10 のみ）は、評価が浅い可能性がある → 採点基準を詳しく適用し直す

### Q: 改善後に再スコアリングしても点数が上がらない

**症状**: 改善を実装したのに、Phase 5 の再スコアリングで点数が変わらない

**対処**:
1. **改善の内容が、実際にスコアリング基準を満たしているか確認**
   - 例: 「Safety Gates フック追加」→ 実装済みか？ `.claude/settings.json` に `PreToolUse` が記載されているか？
2. 改善が部分的だった場合は、「次のステップ」を明確化して追加改善
3. スコアが改善基準の「下限」に近い場合、関連する複数の小項目を同時改善すると点数がより上がる
