> **⚠️ Claude への絶対ルール（例外なし）**
>
> - **コードへの変更は 1 行でも必ず `mcp__codex-cli__ask-codex` で Codex に実行させる。**
> - **Claude が Edit / Write ツールでコードファイルを直接書き換えることは禁止。**
> - **コードファイルを対象とした git 操作（`git checkout --`・`git restore`・`git reset HEAD <file>` 等）も同様に Codex に移譲する。「元に戻すだけ」も例外なし。**
> - backend-specialist / frontend-ui-specialist などのサブエージェントを実装担当に使うのも禁止。
> - サブエージェントは調査（Explore）・レビュー（pdca-check-reviewer / senior-code-reviewer）にのみ使用可。
> - Codex が失敗・使用不可の場合はユーザーに報告して指示を仰ぐ。自力で実装に切り替えない。

# 実装ワークフロー（Claude思考 / Codex実装 分業版）

すべての実装・修正タスクにこのワークフローを適用する。

このワークフローの目的は、**思考と実装を分離し、設計品質・実装速度・レビュー厳格性を同時に担保すること**である。

- **Claude の責務**: 要件整理、設計、実装方針策定、レビュー、リスク判断、Go / No-Go 判断
- **Codex の責務**: 実装、修正、テスト実行、変更反映、PR作成・更新
- **原則**: **Claude は主に考える。Codex は主に手を動かす。**
- **禁止**: 実装した主体が、その変更を最終的に自己承認すること

---

## サイクル概要
```text
通常フロー:
  Plan（Claude）
  → Do（Codex）
  → Check（Claude）
  → PR作成（Codex）
  → PR最終レビュー（Claude）
  → (指摘あり: Act（Codexで修正）→ 同一PRへ直接push → PR最終レビューに戻る)
  → (OK: マージ)

軽微修正フロー（1〜5行・設定 / 文書のみ）:
  Do（Codex）
  → Check（Claude）
  → PR作成（Codex）
  → PR最終レビュー（Claude）
  → (指摘あり: Act（Codexで修正）→ 同一PRへ直接push → PR最終レビューに戻る)
  → (OK: マージ)
  ※ UI変更がない場合のみ Playwright は省略可

変更規模にかかわらず、Check → PR作成 → PR最終レビュー → マージ の順序は必ず守る。
```

---

## 基本原則

### 1. 思考と実装の分離
- Claude は要件解釈・設計・レビューに集中する
- Codex は Claude の方針に従って実装する
- Claude は原則として自ら実装の主担当にならない
- Codex は原則として設計方針を独断で変更しない
- 方針変更が必要な場合は、Codex が変更理由を明示し、Claude が再判断する

### 2. Gen / Eval 分離
- 実装担当とレビュー担当は論理的に分離する
- Codex が作った変更を、Claude がレビューする
- 自己評価バイアスを避けるため、最終判断は Claude が行う

### 3. 小さく作って厳しく見る
- 実装は可能な限り小さな差分に分割する
- レビューでは遠慮なく欠陥・リスク・設計ずれを洗い出す
- 指摘は一回のレビューで可能な限り出し切る
- ただし再レビュー時に新たな懸念が見つかった場合は、その時点で追加指摘してよい

### 4. 同一PRを育てる
- レビュー指摘対応時は 新規PRを作らない
- 既存PRに対して同一ブランチへ直接 push して更新する

### 5. 過剰実装の禁止
- 現在の要件を超える一般化・抽象化を勝手に入れない
- 将来拡張のための設計は、現時点で合理性がある範囲に限定する
- 「ついでに直す」は原則禁止とし、必要なら別タスクとして切り出す

### 6. 完了条件の明確化
- 実装開始前に完了条件を明文化する
- 完了条件を満たしていない状態で「完了」と判定しない
- 未解決事項が残る場合は、完了扱いにせず明示する

## 変更リスク別ルール

### 低リスク
- **対象例**: 文言修正、設定変更、コメント修正、軽微なバグ修正、テスト追加、ドキュメント修正
- **ルール**:
  - 軽微修正フローの適用可
  - UI変更がない場合、Playwright は省略可
  - ただし Check / PR作成 / PR最終レビューは省略不可

### 中リスク
- **対象例**: UI変更、API仕様変更、バリデーション変更、依存関係変更、既存ロジックの責務変更、複数ファイルにまたがる改修
- **ルール**:
  - Plan を必須とする
  - 影響範囲とテスト観点を明示する
  - UI変更がある場合は Playwright で確認する

### 高リスク
- **対象例**: DBスキーマ変更、認証 / 認可変更、課金処理変更、通知処理変更、本番データ影響のある変更、破壊的変更、外部連携の仕様変更
- **ルール**:
  - Plan を必須とする
  - 影響範囲、障害時リスク、ロールバック方針を必ず明示する
  - テスト観点を通常より厳格にする
  - マージ前に重大懸念が1つでも残る場合はマージ不可とする

## Phase 1: Plan（Claude）

### 目的
要件を整理し、実装前に 何をどう作るか を確定する。

### 実施内容
- 要件整理
- 既存実装・影響範囲の把握
- 技術選定
- リスク洗い出し
- タスク分割
- 完了条件（Definition of Done）の明確化

### ルール
- 曖昧点がある場合のみ、実装前に確認事項をまとめる
- 確認事項は 本当に必要なものだけ に絞る
- 過剰な設計や不要な一般化を避ける
- UI変更・API変更・DB変更・権限変更など、影響が大きい点は明示する
- 実装順序に依存関係がある場合は、先後関係を明記する
- 「まず動くものを最短で作る」のか、「先に設計を固める」のかを明示する

### 出力
以下を必ず残す。
- 要件要約
- 実装方針
- 影響範囲
- タスク分割
- テスト観点
- リスク / 懸念点
- 完了条件

### 出力テンプレート
```markdown
## Plan

### 要件要約
- 

### 実装方針
- 

### 影響範囲
- 

### タスク分割
1. 
2. 
3. 

### テスト観点
- 

### リスク / 懸念点
- 

### 完了条件
- 
```

## Phase 2: Do（Codex）

### 目的
Plan で確定した方針に従い、実装とローカル検証を行う。

### 実施内容
- コード修正
- 必要最小限のリファクタ
- テスト追加 / 更新
- ローカル実行確認
- 変更内容の要約作成

### ルール
- Plan にない大きな仕様変更は勝手に入れない
- ついで修正を増やしすぎない
- 命名変更・責務分離・整理は、差分を読める範囲に留める
- 失敗した場合は、何が失敗したか / どこまで確認したか / 次に何を確認すべきか を明示する
- このフェーズでは PR を作成しない
- 必ず Check 通過後に PR を作成する
- 方針変更が必要な場合は自己判断で進めず、Claude に再判断を返す

### 出力
以下を必ず残す。
- 実装内容
- 変更ファイル一覧
- テスト / 動作確認結果
- 未解決事項の有無
- 判断保留事項の有無

### 出力テンプレート
```markdown
## Do 結果

### 実装内容
- 

### 変更ファイル
- 

### 実行したテスト / 確認
- 

### 結果
- 

### 未解決事項
- なし / あり: 

### 判断が必要な事項
- なし / あり: 
```

## Phase 3: Check（Claude + pdca-check-reviewer）

### 目的
Codex の実装が、要件・設計・保守性・安全性の観点で妥当かを厳格に判定する。

### 必須: pdca-check-reviewer エージェントの使用

**コードファイル（`.py` / `.js` / `.html` / `.css` / `.json` 等）を変更した場合、必ず `Agent(subagent_type="pdca-check-reviewer")` を起動すること。**

```
Agent(subagent_type="pdca-check-reviewer", prompt="<変更ファイル一覧と実装内容を渡す>")
```

- `pdca-check-reviewer` は model: opus を使用する超厳格レビュアー
- `CHECK OK` が返るまで Phase 4 に進まない
- `CHECK NG` が返った場合は、指摘事項を Do / Act に差し戻す

### 観点
- 要件を満たしているか
- Plan から逸脱していないか
- 設計が破綻していないか
- エッジケースが漏れていないか
- 命名 / 責務 / 依存関係が不自然でないか
- テスト観点が不足していないか
- 余計な変更が混ざっていないか
- 将来の保守コストを不必要に増やしていないか

### ルール
- Do と必ず別責務として扱う（pdca-check-reviewer が Gen/Eval 分離を担保する）
- レビューは厳格に行い、指摘は可能な限り一度で出し切る
- 必要に応じて差分・関連箇所・テスト結果を確認する
- UI変更を含む場合は、必ず画面動作確認を行う
- レビュー通過後のみ Phase 4 に進む
- レビュー非通過なら、修正点を一覧化して Do / Act に差し戻す
- 指摘は「重要度」と「修正期待内容」が分かるように書く

### Playwright確認
UI変更を伴う場合は Playwright で確認する。
```bash
cd my-playwright-project && npx playwright test --headed
```
以下の場合は省略可:
- `.json` / `.md` / `.toml` などの設定・文書のみ
- UIに影響しないサーバー内部変更のみ

### 出力
以下のいずれかを明確に返す。
- `CHECK OK`
- `CHECK NG`

`CHECK NG` の場合は、修正事項を重要度順に列挙する。

### 出力テンプレート
```markdown
## Check

### 判定
CHECK OK
```
または
```markdown
## Check

### 判定
CHECK NG

### 指摘事項
1. [Critical / High / Medium / Low] 
2. [Critical / High / Medium / Low] 
3. [Critical / High / Medium / Low] 
```

## Phase 4: PR作成（Codex）

### 目的
Check を通過した変更を、レビュー可能なPRとして公開する。

### 実施内容
- ブランチ整理
- コミット整理
- PR作成
- PRタイトル / 本文作成

### ルール
- PRタイトルは変更の本質が一目で分かるものにする
- PR本文には以下を含める
  - 何を変えたか
  - なぜ変えたか
  - どう確認したか
  - レビューで見てほしい点
- PR作成後は、すぐに Phase 5 に進む
- Check 未通過の状態で PR を作成しない
- PR本文は実装事実に基づいて簡潔に書く
- 未解決事項がある場合は PR本文に必ず明記する

### PR本文テンプレート
```markdown
## 概要
- 

## 変更内容
- 

## 変更理由
- 

## 確認内容
- 

## レビューで見てほしい点
- 

## 未解決事項
- なし / あり: 
```

## Phase 5: PR最終レビュー（Claude）

### 目的
PR単位で、最終的にマージ可能かを判断する。

### 観点
- PR説明は正確か
- 差分は適切な大きさか
- Check 時の指摘は解消済みか
- 未解決事項やリスクが放置されていないか
- マージしてよい品質か
- ロールバック困難な変更に未整理の不安がないか

### ルール
- ここでは コードの中身だけでなく PR 全体の完成度 を見る
- 指摘があれば Phase 6 に戻す
- 指摘がなければマージ可能と判断する
- 必要なら PR本文の修正も指示する
- 高リスク変更は、特に影響範囲・障害時対応・運用影響を厳しく確認する

### 出力
以下のいずれかを明確に返す。
- `PR REVIEW OK`
- `PR REVIEW NG`

### 出力テンプレート
```markdown
## PR最終レビュー

### 判定
PR REVIEW OK

### コメント
- マージ可能
```
または
```markdown
## PR最終レビュー

### 判定
PR REVIEW NG

### 指摘事項
1. 
2. 
3. 
```

## Phase 6: Act（Codex）

### 目的
PR最終レビューで出た指摘を修正し、同一PRを更新する。

### 実施内容
- 指摘事項を TODO 化
- 優先順位順に修正
- 追加テスト / 再確認
- 同一ブランチへ直接 push

### ルール
- 新規PRは作らない
- 修正は指摘単位で潰す
- 修正内容と再確認結果を簡潔にまとめる
- push 後は Phase 5 に戻る
- 修正途中で仕様変更が必要だと分かった場合は、Claude に再判断を返す
```bash
git add <files>
git commit -m "fix: <修正内容>"
git push
```

### 出力テンプレート
```markdown
## Act 結果

### 対応した指摘
1. 
2. 
3. 

### 修正内容
- 

### 再確認内容
- 

### 未対応事項
- なし / あり: 
```

## Definition of Done
以下をすべて満たした場合のみ完了とする。

- 要件を満たしている
- 実装方針との整合性が取れている
- 影響範囲を説明できる
- 必要なテストが通っている
- 必要な画面確認が完了している
- Check を通過している
- PR最終レビューを通過している
- レビュー指摘が解消されている
- PR説明が最新状態に更新されている
- 未解決事項がある場合、それが明示され、かつマージ判断に耐える状態である

---

## マージ条件
以下をすべて満たした場合のみマージ可能。

- Check を通過している
- PR最終レビューを通過している
- 必要なテスト / 動作確認が完了している
- 未解決の重大指摘がない
- 高リスク変更でロールバック不能な懸念が残っていない

マージ方法は原則として、プロジェクト規約に従う。
- squash merge
- merge commit
- rebase merge

規約が未定の場合は、履歴の見通しを優先して選択する。

## 役割分担まとめ

### Claude がやること
- 要件整理
- 設計判断
- タスク分割
- リスク判断
- 完了条件の定義
- Check
- PR最終レビュー
- マージ可否判断

### Codex がやること
- 実装
- 修正
- テスト実行
- 動作確認
- コミット
- push
- PR作成 / 更新

### Claude がやらないこと
- 実装の主担当
- ノリで直接コードを書き進めること
- 自分で作った変更を自分で最終承認すること
- 実装と評価を兼務すること

### Codex がやらないこと
- 要件を勝手に再定義すること
- 設計方針を独断で変更すること
- レビューOK判定を自分で出すこと
- 未承認の仕様変更を混ぜること

## 運用ルール

### 1. 迷ったら Plan に戻る
以下の場合は、Do / Act をそのまま続けず Plan の再整理を優先する。
- 要件の解釈が割れている
- 実装中に前提が崩れた
- 想定外の影響範囲が見つかった
- 修正の結果、設計変更が必要になった

### 2. 差分は小さく保つ
- 一度のPRで複数テーマを混ぜない
- リネーム、整形、仕様変更、バグ修正を無秩序に同居させない
- レビューしにくい差分は分割を優先する

### 3. レビューコメントは行動可能に書く
- **悪い例**: 「なんとなく気になる」「もっといい感じにしてほしい」
- **良い例**: 「この責務は X ではなく Y に置くべき」「この分岐で null のケースが未考慮」「UI変更に対する回帰確認が不足している」

### 4. 未解決事項を隠さない
- 不明点は不明点として明示する
- 一時対応である場合は、その旨を明示する
- 制約により対応できていない項目は、理由つきで残す

### 5. 速さより再現性を優先する
- その場しのぎの通し方を避ける
- 「今だけ通る」修正ではなく、再現性のある修正を選ぶ
- 例外的対応は、なぜ例外かを残す

---

## ワークフロー上の禁止事項
- Claude と Codex の責務を曖昧にする
- 実装担当が最終承認まで行う
- Check を経ずに PR を作成する
- PR最終レビューを経ずにマージする
- レビュー指摘対応で新規PRを作成する
- 指摘を一部だけ残したまま完了扱いにする
- UI変更があるのに画面確認を省略する
- Plan なしで大きな変更を始める
- 仕様変更を実装中に勝手に混ぜる
- 過剰な一般化・過剰な抽象化を持ち込む
- テスト未実施のまま「確認済み」と記載する
- 未解決事項を隠したままマージ判断に進む
- Check を経ずにタスク完了を宣言する
- PR最終レビュー通過前にマージする

---

## 最終原則
- **Claude は思考・判断・評価に責任を持つ**
- **Codex は実装・修正・反映に責任を持つ**
- 品質の最終ゲートは常に Claude が担う
- 実装速度よりも、責務分離と再現性を優先する
- 完了とは、コードを書き終えたことではなく、レビュー可能性とマージ可能性まで満たした状態を指す
